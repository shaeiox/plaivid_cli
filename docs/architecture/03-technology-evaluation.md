# 03 — Proposed Technology Evaluation

**Audit date:** 2026-10-30. PyPI versions below were queried on this date; they are current registry observations, not tested pins.  
**Decision status:** Proposed recommendations only. No packages were installed.

## Evaluation criteria

The product is Linux-only, local-PVM in this phase, and targets Python 3.12+. Existing source is standard-library-only and uses local PVM CLIs. A dependency should provide material functionality not already adequately available in the standard library, and its runtime/build cost must be measured on representative PVM hardware. “Adopt” means suitable to include in the planned stack subject to a compatibility spike and lockfile; it does not authorize implementation in this phase.

## Proposed dependency profiles (not lock data)

- **Likely application runtime:** Textual (which brings Rich), Typer, selected Pydantic boundary models. Add a direct Rich dependency only if the application directly imports it beyond Textual's APIs.
- **Conditional runtime:** psutil only if PVM metrics do not cover an approved local monitoring requirement; SQLite only for an approved app-owned persistence use case (stdlib `sqlite3` first).
- **Development/CI only:** uv, pytest, Ruff, Pyright. Add pytest-asyncio and Hypothesis when test cases justify them.
- **Defer pending concrete need:** SQLAlchemy, Alembic, HTTPX, structlog, tenacity, platformdirs, pydantic-settings.

Keep the shipped runtime as small as practical. Avoid collecting proposed libraries into one dependency set simply because they appear in the initial technology list.

## Textual + Rich validation

Textual's upstream repository describes it as an asynchronous terminal application framework with widgets (including data tables), layouts, and testing support: [Textual repository](https://github.com/Textualize/textual). That matches the proposed UI better than expanding hand-written ANSI redraw logic, but the repository itself does not prove performance or packaging fit for this PVM environment.

| Need | Framework support | App-specific work / validation |
|---|---|---|
| Flicker-free/partial updates | Textual manages terminal rendering and can update changed widget render output; it is materially different from the current clear-screen loop. | Verify flicker in target terminals, including full repaint on resize and table refresh. Do not build a separate dirty-region system until profiling demonstrates need. |
| Large inventory table | `DataTable` supports tabular presentation and keyboard interaction. | Benchmark representative and upper-bound VM counts, row updates, sorting, filtering, and memory. Confirm whether rows/cells are retained in memory; paginate/virtualize if measurements require. |
| Keyboard navigation | Widget focus, bindings, selection, and message handlers are native primitives. | Define command shortcuts, focus order, discoverability, confirmations, and accessible status/error interactions. |
| Responsive layouts | Textual CSS/layout and terminal-size events are native. | Design meaningful narrow-terminal behavior; test minimum terminal sizes and resize churn. |
| Progress and notifications | Textual widgets/notifications and Rich progress/renderables provide primitives. | Map operation lifecycle to application events; define transient vs persistent errors and per-VM bulk progress. |
| Long-running operations | Textual is async internally and supports worker patterns. | Move blocking `sbell` subprocess calls out of the UI event loop (thread/async subprocess worker); support cancellation/timeouts and serialize mutation safely. |
| Memory/CPU overhead | Framework provides features but adds more runtime objects/code than current stdlib renderer. | Measure idle baseline, refresh CPU, memory, and table update cost in a PyInstaller artifact on representative PVM hardware. |
| Testability | Textual includes application testing/pilot facilities. | Add deterministic fake provider and test screens/keyboard interactions; still run a small terminal integration matrix. |

**Diff-based rendering proposal:** Adopt Textual's widget invalidation/diff rendering first. Do not layer an independent `ChangeDetector → DirtyTracker` renderer onto it by default. Snapshot change detection is still useful for deciding whether domain state changed and suppressing unnecessary updates/events; Textual should own terminal-cell diffing. Prototype whether stable widget identities and minimal data updates avoid visible full-table churn.

## Comparison beyond proposed framework

No alternative warrants selection now. Prompt Toolkit is worth a targeted comparison only if a command-prompt-first interface or advanced line editing remains central; current `readline` is already a command prompt with completion. A hand-built TUI is not a meaningful default alternative for the proposed responsive, keyboard-navigable application because the repository already shows the maintenance surface of bespoke layout and terminal handling. Revisit only if Textual fails a measured compatibility or packaging constraint.
