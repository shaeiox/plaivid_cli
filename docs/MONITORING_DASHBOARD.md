# Overview monitoring dashboard: validation status

This is the **active Textual** Overview, not the excluded legacy `commands/overview.py` / `render.py` renderer. It is a local Linux client, not an SSH client. No remote monitoring agent or production-host software is installed.

## Visual system

Plaivid adapts the [Gemini CLI TUI design guide](https://github.com/cola-runner/awesome-tui-design/blob/master/designs/gemini-cli/DESIGN.md) to the detected terminal color depth. Truecolor keeps the blue-black/purple layers, but the wordmark is now one solid accent instead of a gradient. The interface follows the [project-local Unslop skill](../.agents/skills/unslop/SKILL.md) by Damir Sokolovsky (CC BY 4.0): restrained chrome, sentence-case headings, consistent one-line controls, and semantic status color. See [the audit and task plan](TUI_UNSLOP_PLAN.md). A 256-color terminal places panels and cards on the same dark canvas (xterm index 233), with subtle neutral borders and restrained accents; separate gray fills looked like blocks, while automatic downsampling of the truecolor surface would produce saturated navy (index 17). Standard 16-color and `NO_COLOR` output use a legible high-contrast fallback. Statuses remain labeled in text. Textual built-in controls and explicit widget CSS receive the **same** palette, including on older releases that lack the theme API. Both 80- and 120-column layouts have been checked with local Textual Pilot renders. There is no high-frequency spinner: monitoring status colors change only with real collection state.

The color mode depends on the terminal session, not the name of the shell. `TERM=xterm-256color` alone advertises 256 colors, not truecolor; `COLORTERM=truecolor` or a capable Windows console may enable full RGB. Do not force `TEXTUAL_COLOR_SYSTEM=truecolor` unless the terminal really supports it. SVG screenshots always export as truecolor and cannot by themselves validate the terminal's ANSI output.

## Operator controls

- After login/resume: **Overview** first, **Virtual Machines** second. Both pages use single-row actions and consistent three-row toolbars; the VM list shows concise columns at 80 columns, while the selected VM detail retains its full UUID. `1` / `2` switch pages (when a text field is focused, digits edit that field). `R` refreshes the active page; `Enter` inspects the selected VM; `Q` quits. Both inventory pages offer local name search; search does not collect from PVM and moves selection to the first visible match (or clears it when none match). Apply to all targets the **unfiltered** inventory, never only visible search results; the VM scope line names this explicitly. Clear search on logout. VM lifecycle operations remain on Virtual Machines. Audit is opened with its secondary **Audit** button there.
- Overview's top bar shows `Refresh: 3s` by default. Enter a whole number of seconds from **1–60** and select **Apply**. Invalid input leaves the prior interval in place. The setting changes local collection scheduling without restarting; it does **not** relax VM operation freshness policy or accelerate the expensive dashboard/inventory call below its 18-second minimum. A manual **Refresh** is explicit; **Rediscover** requests `network nic-list` again.
- Host resource numbers come from local `/proc` (CPU uses consecutive samples; RAM uses MemAvailable); PVM-reported identity and raw RAM values are labeled separately. If Plaivid runs on a different Linux machine than the PVM host, **local** resource numbers describe that machine, not the PVM. Never treat this distinction as a verified host-ID match.
- NIC tabs require a recognized `network nic-list` schema *and* a matching local physical sysfs device. Each discovered physical device is sampled even if not selected. RX/TX rates require two successful counters and elapsed time. Unsupported counters and CRC show `N/A`; an existing sysfs CRC counter is used if exposed by the driver. The NIC-list parser maps the captured `sbell network nic-list` schema (`tests/fixtures/nic-list.xml`): `<device>` is the Linux interface name used for the sysfs check, and `<name>` (e.g. `NIC4`) is kept as the PVM identifier. Records missing either field fail closed.
- The **RUNNING VMS** card and VM monitoring summary use the last numbered `ROW` from a complete `pvm-running-vms` listing (for example, a validated sequence `1` through `6` reports **6**). The parser accepts the listing title, header, and VCPU/Memory totals, checks row numbering and the reported VCPU sum when available, and marks malformed/truncated/nonzero-exit output partial. Missing rows, empty output, or unnumbered synthetic process observations show N/A rather than an invented zero. This is a count of the helper's observed running processes, **not** a count inferred from VM object-store states; unmatched process UUIDs do not suppress the helper's count. A previously verified count can be displayed during a stale read with a warning/age label, not as a fresh count.
- Collector results and timestamps drive each card's status label; a missing or failed PVM read is not proof of the host being powered off. An unsupported NIC source is a warning, not a false claim of healthy monitoring. The Overview no longer shows a host heartbeat, collection-health line, VM status summary, or virtual disk image panel. VM top-list fields remain N/A until the installed API contract is verified. **Container monitoring is excluded.**

## Host monitoring panels (`sbell monitoring metrics`)

The Overview's **Host monitoring** section is built from one `monitoring/metrics` response per refresh cycle. Cards: System information (host, host ID, platform, kernel, virtualization, boot time, sballd and server uptime), CPU (usage, cores, run queue, blocked tasks, context switches, interrupts, forks), Memory (RAM and swap), Load & tasks (load averages, task, process, thread and open-fd counts), Network interfaces, Storage (real filesystems only), Temperature, Sessions (logged-in users), and Host status. Host status (from `sball show`) sits under Load & tasks in the centre column and shows the logo, node name and IP, sball and node state (green when quorate or up), and the release version (accent colour). Top processes by CPU is a full-width card: the top 8 are shown from the 50 kept, with a **Command summary** beside them that counts every process by command name.

Responsive layout: the card grid has 3 columns at 130 or more terminal columns, 2 columns at 90 to 129, and 1 column below 90. The process table and command summary sit side by side only at 3 columns; below that they stack. No card uses glow.

Rules: a missing value is shown as `—`, never as zero. The process `full_command` field is never read or displayed, because it can contain sbell argv and session tokens. Units for the per-process memory percentage are taken as reported and are not independently verified on the target host. Synthetic test fixtures live in `tests/fixtures/monitoring-metrics.xml`.
